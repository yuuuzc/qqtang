# 结婚系统

日期：2026-08-16（Asia/Shanghai）

结婚关系使用独立的 SQLite 关系模型。人物协议中的 `SpouseUIN` 只是从关系表生成的投影，
不会把两个账号的关系重复塞进人物 JSON。配偶昵称也在读取时从当前人物档案取得，因此改名后
不需要修补第二份婚姻缓存。

## 已实现链路

- 求婚：`0x0104 → 0x0105`，对应消息表 `REQUEST/RESPONSE/NOTIFY_SPARK`
  (`0x0BEA..0x0BEC`)。双方必须在线、未婚且未参与另一份待处理求婚；发起者须持有
  “水晶之恋” `9020`。原物品说明只证明“求婚必备”，没有证明成功后消耗，因此当前按持有资格
  处理。待处理求婚十分钟失效。
- 接受或拒绝：`0x0106`，对应 `REQUEST/RESPONSE_ANSWER_SPARK`
  (`0x0BED/0x0BEE`)。接受时在同一事务创建一条婚姻和两个唯一成员；拒绝只删除待处理请求。
  原版上行字段是 `UIN=应答者、DstUIN=求婚者`，服务端响应才恢复为
  `UIN=求婚者、DstUIN=应答者`；两条方向不能复用同一身份顺序。成功求婚响应使用非空说明，
  避免发起端弹出空结果窗口。
  成功后双方在线人物档案立即重新投影，登录、大厅资料和房间成员继续使用原版 `SpouseUIN`
  字段。
- 婚姻资料：`0x0107 / 0x0BEF..0x0BF0`，返回双方昵称、结婚天数、忠诚、等级、等级值、
  爱情宣言和戒指编号。结婚天数按持久化时间计算，不随重启丢失。双方有效背包中的最高戒指
  `9021..9026` 会把真实ItemID同步为 `RingID`；多枚并存时显示最高档，移除或失效后下次读取会
  降级/归零。
- 修改爱情宣言：`0x0108 / 0x0BF1..0x0BF2`。文本按原结构的 200 个 GBK 字节上限验证。
- 离婚：`0x0109 / 0x0BF3..0x0BF4`。关系和双方成员在同一事务删除，并向在线配偶发送通知；
  删除任一账号也会由外键和触发器清理幸存者的配偶投影。
- 婚礼房：`0x010A..0x010E / 0x0BF5..0x0BFC`。婚礼只能由聊天房房主向同房在线配偶发起；
  中式/西式模式分别是 `1/0`。确认对象、待确认状态和活动状态属于房间权威状态，不能接受其他
  房间或过期对象的确认；任一新人离房会清理本场婚礼状态。

数据表为 `marriages`、`marriage_members`、`marriage_proposals`。同一账号最多存在于一条婚姻，
同一账号同时最多参与一份有效求婚；SQLite schema 13 会在旧存档上原地创建这些表。

## 戒指官方资源与保留边界

客户端官方物品表和对象归档共同确认六枚戒指商品 `9021..9026`，最后一枚为“永恒爱神之戒”。
婚姻资料界面对正数 `RingID` 直接读取 `object/ui/marriage/ring/ring%d.img`；原始对象归档恰好自带
`ring9021.img..ring9026.img` 六张120×112婚姻专用DIMG。因此 `RingID` 的正确线值就是ItemID
`9021..9026`，不是档位1..6。此前空框和左上小图均由错误下发档位后请求不存在的 `ring1..6`
引起；用56×53商品卡面生成20×19/99×99图片及修改控件矩形都已撤销。

当前准备客户端保持原版 `uiMain.pyc` 与原版 `object.idx/pkg`，六张官方大图直接使用原始客户端
自带资源。详见 `evidence/marriage-ring-official-assets-v3.md`；该证据取代EVID-230/240/244/271中
关于档位线值和派生资源的结论。

忠诚度、婚姻升级阈值和婚后事件的原服公式也尚无可靠 5.2 数值表。新关系使用客户端可显示的
一级基线；本轮不伪造在线时长、对局或消费带来的增长。婚礼演出依赖原版聊天房界面，协议、事务
和房间状态已经完成无 UI 回归，仍需后续双客户端逐按钮验收。

应答双方字段的静态合同与回归见 `evidence/marriage-answer-identity-contract-v1.md`。
