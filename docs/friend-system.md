# 好友系统

日期：2026-08-16（Asia/Shanghai）

好友关系使用有方向的 SQLite 关系，而不是把两个账号强制绑定成一条对称记录。原版客户端收到
好友申请后，如果勾选“同时加对方为好友”，会先发送一份反向 `DoFriendTask(..., 1)`，再发送
同意 `DoFriendTask('y', ..., 6)`；所以服务端只有实际收到反向申请时才建立双向关系。

## 已实现链路

- 读取列表：transport `0x00A2`，请求 schema `0x10FE` 固定 8 字节，响应 schema `0x10FF`
  固定 810 字节。响应始终保留 200 个 UIN 槽，`CurrentFriendNum` 决定有效项数量，不能按当前
  好友数缩短数组。
- 添加申请：transport `0x00A3`，request schema `0x1100` 的消息表上限为 526 字节，其中
  14 字节头后最多承载 512 字节 `Word`。原版客户端实际上发送紧凑的
  `14 + WordLength` 字节；兼容实现也接受尾部全零补齐到 526 字节，但拒绝声明长度之后的
  非零数据。`Word` 是 GBK 编码的“发送者固定昵称槽 + 申请文字”，其中的内嵌 NUL 必须原样
  保留。目标在线时保存待处理申请，并向目标主动推送未关联 response 的同一份
  `0x00A3 / REQUEST_ADD_FRIEND (0x1100)`；客户端由此在聊天栏显示申请信封。目标离线或校验
  失败时立即向请求者返回拒绝结果。
- 同意/拒绝：transport `0x00A6`，schema `0x1105` 固定 14 字节。接受时提交申请者持有的有向
  好友关系；若接受者已经先发出反向申请，则同一事务提交第二个方向。拒绝只消费待处理申请。
- 删除：transport `0x00A4`，请求 12 字节、响应 10 字节，只删除操作者自己的有向关系。
- 资料与状态刷新：transport `0x00A5`，schema `0x1104` 固定 163 字节。好友列表响应后逐项
  推送昵称、性别、竞技/探险积分、身份、在线状态和当前在线角色的最多 30 件外观；登录与正常
  离线也向所有把该玩家列为好友的在线账号推送状态变化。
- 追踪好友继续使用独立的 `0x0067 REQUEST/RESPONSE_FIND_FRIEND`，不是好友列表命令。客户端
  菜单中的屏蔽/取消屏蔽由本地 `GetAttribute` 状态控制，当前消息表没有对应的服务端关系协议，
  不将其伪装成持久化好友操作。

数据表为 `friendships` 和 `friend_requests`，SQLite schema 14。账号删除由外键级联清理两张表；
每个有向列表最多 200 人。所有好友请求还必须满足 envelope UIN、payload UIN 与已认证会话 UIN
三者一致，不能代表另一个在线账号操作。

## 证据边界

当前客户端通过在线玩家资料发起申请，接收方依赖实时、未关联请求的
`REQUEST_ADD_FRIEND` 通知。QQTSection 对 transport `0x00A3` 按关联方向选择对象：未关联通知解码
为 `0x1100` 并进入 `ReceivedRequestAddFriend(uin)`；只有与客户端自身请求关联的返回才解码为
`0x1101 RESPONSE_ADD_FRIEND` 并进入结果处理，后者不能代替接收方申请通知。没有发现离线申请
重放列表或离线消息 schema，因此当前只允许向在线玩家发起申请，不猜造跨重启的离线弹窗。
待处理记录只用于保证同意/拒绝和双向申请的事务一致性。

数组上限来自客户端消息表 396..403；`0x00A3` 的真实紧凑长度来自原版客户端实抓，request / response
对象选择来自 QQTSection 的 `FUN_1000faa9` 与 `FUN_1000fc4e`，详见
`evidence/friend-request-envelope-contract-v1.md`。“同时加对方”顺序来自
`runtime/analysis/client-python/res/uiRes/uiMain.py` 的接受按钮实现。无客户端自检覆盖双向申请、
接受、双方列表和双方删除；协议测试覆盖固定 810/163/14/12/10 字节结构、申请紧凑/全零补齐两种
编码、身份拒绝、目标 request 原样转发和在线角色装扮投影。原版好友页的逐按钮 UI 演出仍需在
新服务端部署后完成双客户端验收。
