# QQ堂宠物目录与资源审计

数据边界：`PetTypeID` 是宠物实体类型，不是 `itemCFG` 背包道具 ID；两者不得混用。

## 服务端生命周期

客户端 `REQUEST_HANDLE_PET (0x0BCD)` 的 EventID 已类型化为：1 喂食、2 携带、3 停止携带、4 放生、5 改名、6 学习技能、7 使用宠物卡领养。

- Event 7 通过下表的 canonical 宠物卡 ItemID 找到 PetTypeID，在同一 SQLite 事务中扣一张卡并创建独立宠物实例；同种宠物或宠物栏已满时不扣卡。
- Event 6 通过 `itemCFG` 的 `skill` resource ID 得到一字节 SkillID，在同一事务中扣一本技能书并更新 `PET_BASE_INFO.Skills`；已学技能、同等级技能冲突或技能栏已满时不扣书。
- Event 2/3 同步 `player_pets.state` 与人物档案 `GameInfo.PetID`；携带另一只宠物会在同一事务中先停用原宠物，并由 SQLite 部分唯一索引保证每账号至多一只 `state=1`。Event 4 原子清除被放生宠物及活动引用；Event 5 使用 12 字节 GBK 名称上限。
- Event 4/7 会在成功响应后沿原生宠物 `route=4` 主动下发完整权威列表：领养先推送宠物卡绝对剩余量再刷新列表，放生直接刷新列表。原客户端不会可靠地把成功响应中的单条记录解释成集合增删；旧实现因此必须关闭再打开宠物页才可见。
- Event 1 的九种食品按已恢复的原版数值更新体力、成长与心情并原子扣除库存，属性与成长等级均执行客户端上限。
- 宠物卡说明中的“具有天赋”会在启动时与 `PetCfg.ini` 的原生 `SkillName` 表连接，得到每个 `PetTypeID` 的 0～3 个基础技能。它们在宠物列表、宠物操作回包和房间成员内嵌的完整 `PET_BASE_INFO` 中投影，但不写入 `player_pets.skills`；技能书学到的 51 及以上技能仍作为账号状态单独持久化。房间投影只保持宠物资料一致，不触发技能效果。客户端原生界面明确把 `SkillID<=50` 放入 3 格基础技能区，把其余技能放入独立的 10 格学习技能区。
- 结算不依赖上述 UI 投影：携带宠物的卡片 ItemID 直接提供基础天赋效果，已学习 SkillID 再映射回对应技能书 ItemID；竞技积分/糖币和探险勇气/材料均从同一目录规则计算，因此退出、重试或房主迁移不会改变技能来源。

`QQTMsgData.bin` 表中的 `PET_BASE_INFO=58`、`RESPONSE_HANDLE_PET=266`、`RESPONSE_PLAYER_PETS_INFO=1452` 是解码后最大结构尺寸，不是固定线包长。`Skills`、基础宠物数组、扩展宠物数组和错误原因均按计数紧凑发送。旧实现补齐全部容量，导致第一只宠物尚可显示、第二只开始从技能补零区错位读取，表现为宠物页整体为空。2026-08-14 原版客户端实测修复后两宠物响应由 1530 字节总包缩为 154 字节总包，列表、翻页及连续“携带→休息→携带”即时生效。

协议和调用点证据见 `evidence/pet-chat-emotion-protocol-v1.md`。
