# 探险房间与关卡会话

## 已实现链路

房主明确选择探险地图时，客户端通过命令 `0x0078` 发送 `REQUEST_MODIFY_ROOMINFO`。已确认的 15 字节请求字段为 UIN、客户端时间、MapID、GameType 和尾部四字节值。2026-08-05 16:42 的真实地图 1601 选择携带尾值 `0`，而本地 `Continue.ini` 的路线号为 `1`，因此该尾值不能继续当作路线号验证。服务端现在以可选首关 MapID 为实时固定选择依据；只有关间 `0x1178` 才按已确认语义验证 ContinueID 和 NextMapID。地图选择不写入人物 SQLite。

客户端的房间创建默认“随机地图”不会发送一个特殊地图 ID，也不会用 `0x0078` 把先前的固定选择清零。2026-08-07 12:06 的实际会话只在第一次明确选择时发送一次 `0x0078`（MapID 1607），后面新建四个随机房间均没有再次发送该命令；旧服务端却把连接级 MapID 1607 复用于五个 GAME_BEGIN。Go 现把选择建模为房间级 `Random` 或 `Fixed(MapID)`：每个新房间从 `Random` 开始，固定选择只修改当前房间，随机房间在每次对局开始时从客户端已安装的 `Continue.ini` 路线首关中等概率抽取。废弃的 `default_adventure_map_id` 配置及其 1601 启动校验已移除。

开始游戏不再调用写死的“魔法王国 1”构造器。服务端从只读工作副本的 `map/mapDesc.py` 取得地图文件名，计算 `Map/<file>` 的大写 ASCII MD5，并从 `Continue.ini` 取得本地路线和关卡顺序。开局 `GAME_BEGIN_DATA` 使用实时 MapID、地图哈希以及新的 SpawnSeed、ItemSeed。

`GAME_BEGIN_DATA.ContinueID` 不是上述本地 `SequenceID`。动态版本曾错误地把本地路线号写入该字段，并把 `battlefield_map<ID>.dat` 的原始 MD5 写入 FileHash；真实运行随即进入 `_room_data::CheckContinueFiles`，显示“下载地图文件，请重新开始游戏”。此前可进图的已验证包使用 `ContinueID=-1`、FileHash 全零。当前代码用类型常量 `NoRemoteContinueFileID` 明确表示“全部续关资源已安装在本地”，不再触发已停用的官方下载链。

`PLAYER_GAME_INFO.ExtPoint` 现在来自持久化人物的 `GameInfo.ExtPoint`。客户端自身解包后的 `PVEDATA` 明确给出最高 `lev_30 point="428326799"`，当前存档已使用这一精确阈值；它会同时出现在登录人物属性和进图开局包中，客户端不会再按零探险经验回退到 300 点基础血量。

每关完成后，客户端在游戏事件命令 `0x0083` 的 `0x03FB / REQUEST_PLAY` 中发送 `0x1178 / REQUEST_GAME_NEXTMAP`。长度对象里的 GameData 以四字节小端 DWORD schema 开头，后接 14 字节业务主体 PlayerID、ClientTime、ContinueID 和 NextMapID；此前把 schema 的高 16 位误命名为 `GameDataSequence`。最后字段实际为 `1602`，不是此前假定的数组索引。服务端同时验证玩家、路线和由 `Continue.ini` 推导出的 NextMapID；关联 `0x1179` 响应仍使用命令 `0x0083` 的 REQUEST_PLAY 外壳，主动 `0x1177` 下一关通知则使用命令 `0x0084` 的 `0x041B / NOTIFY_GAME_EVENT` 外壳。魔法王国 1 的权威顺序为 `1601→1602→1603→1604→1605→1606`，其余 11 条路线同样从本地清单加载。

原版多人探险换关还包含淘汰分流：进入下一关时，已经死亡的玩家不会复活或继续留房，而是个人结算后退出；只有存活玩家进入下一张图。`AdventureStageTransition` 已把结果建模为 `Survivors` 和带明确原因的 `SettledOut`，下一关对局只用 Survivors 重建，共享房间状态也按 `EliminatedBetweenStages` 移除后者。

仲裁者属于房间/战斗状态，不是协议编码器默认值。开局从真实房间参与者中显式选择，编码器拒绝不在 Players 中的 ID；角色死亡不会让仍在本关的客户端失去仲裁资格，且死亡成员仍可由存活队友使用医疗包救回。下一关若原仲裁者仍在 Survivors 中则保留，否则从 Survivors 迁移。主动离开和连接断开才从本关候选集移除；离开者是仲裁者时立即从其余仍连接的探险参与者中迁移，但若已经无人存活则按失败结束。TCP 关闭已经接入该状态机：先用普通 `NOTIFY_LEAVE_ROOM` 更新成员/房主并触发客户端内部唯一一次 `0x10EC` 玩家清理，再用专用 `0x0FB1 / NOTIFY_CHANGE_ARBI_PLAYER` 把新 PlayerID 写入活动场景仲裁指针。不能再把 `NOTIFY_LEAVE_ROOM.NewArbitratorID` 字段本身当成场景切换动作，也不能由服务端额外发送第二个 `0x10EC`。关间死亡成员先在同一权威事务中全部移除，再把该批每一条离场事实投影给每个淘汰端和幸存端；所有通知都携带最终房主/仲裁者，不能让任何淘汰端残留另一名同批淘汰者。房卡刷新后才发送各自失败 GameOver，只有 Survivors 收到下一关通知。死亡的旧仲裁者也在这一步退出候选，下一关消息携带幸存者中的新仲裁者。

## 房间与对局生命周期

房间是长期准备容器，对局是房间启动的一次运行实例。Go 的房间对象现在独立保存 RoomID、房主、成员、角色/队伍/准备快照、`Random`/`Fixed` 地图选择、实时模式、状态修订号和 ActiveGameID；地图选择不再只是连接上的裸变量。正常开始和结束的状态为 `Preparing → InMatch → Settling → Preparing`，结束时保留原房间、成员、房主和地图选择/模式，仅删除 battle、清零 ActiveGameID 并重置准备状态；离开后新建房间则重新回到 `Random`，不会继承上一房间的固定 MapID。

主动中途退出、关间死亡淘汰和掉线是活动对局离房原因，不与正常结算共用路径；准备房踢人只移除房间成员并保留大厅连接，活动对局中不允许踢人。房主离开而房间仍有人时迁移房主，空房才回收。后续命令表与完整会话已确认 `0x0069` 是 `REQUEST_LEAVE_ROOM`，不是“玩家信息刷新”。对局仍活动时收到它表示主动退出对局并离房；正常 `GAME_OVER` 后，原版客户端还会用同一命令销毁本地游戏场景，但此时只应把成员送回已恢复为 Preparing 的原房间。

2026-08-06 的旧样本曾把结算后 `0x0069` 误判为“回大厅确认”，并据此清理成员；后续又曾把没有完成GameID关联的所有首包一概吞掉，两者都会制造成员或房间幽灵。QQTSection 静态链找到房主单人场景的300-tick生产者，但2026-08-15三人实机又捕获非房主在GAME_OVER约7秒后发送同一命令，证明该静态链不是唯一来源。服务端现只按每个连接的已完成GameID、Preparing/无ActiveGameID和仍在房间三项消费一次性场景关联，不再按房主身份猜测；关联在GAME_OVER后30秒过期，同一成员第二次请求或过期后的首次请求都是真实离房。直接开始下一局或新成员加入也会清除旧关联。周期 `0x0066` 在房间内同样存在，不能证明玩家进入大厅。

房间内角色选择使用已确认的 `0x0071`：UIN、ClientTime 和 wire uint16 RoleID。RoleID 23 是问号“随机角色”占位符：UI 对它清空名称、立绘和全部能力条，不能作为实体进入 GAME_BEGIN。房间成员与在线会话保留 23；开始对局时才按 `configs/role-rules.json` 将本局快照解析为具体角色。探险池只有正常角色，竞技池另含隐藏实体 10、11、12；紫钻角色 13–16 永不随机。解析结果不写回房间、会话或 SQLite，所以结算回房仍为问号。创建房间请求/响应不携带 RoleID，进入地图的权威值来自 GAME_BEGIN Players。

房间八色队伍使用相邻的 `0x0070 / REQUEST_CHANGE_TERM`，正式字段 TermID(uint16) 即 TeamID 1..8；服务端关联响应后以 `0x007A / NOTIFY_CHANGE_TERM` 广播 PlayerUin、PlayerID 和 NewTermID。队伍颜色只属于当前房间成员，不写人物存档。`PLAYER_INFO_IN_ROOM_OLD.TermAndSeat` 把队伍放在高半字节、座位放在低半字节；绿色队伍 4、座位 1 的实测值为 `0x41`。探险战斗则是单一协作阵营：客户端 `Client+0x20C148` 会根据 `PLAYER_GAME_INFO.TeamID` 决定构造救援 `0x0FAA` 还是击杀 `0x0FA8`，异色开局会令医疗包无法产生救援请求。因此探险 `GAME_BEGIN` 及后续关卡统一投影为红队 TeamID 1，但房间快照继续保留玩家所选颜色；竞技仍继承真实颜色用于分队。

数据归属保持分层：人物属性、背包、战绩和经验属于动态业务数据，写入 SQLite；奖励策略和本地服务参数属于可编辑静态策略，保存在 JSON；地图、路线和资源哈希来自完整客户端已有的 `mapDesc.py`、`Continue.ini` 与 `.map` 文件。当前房间所选地图只是实时会话状态，既不写人物数据库，也不在 Go 中维护一份硬编码地图表。

## 地图物品和掉落

确认部分：静态地图几何来自客户端 `.map`，怪物/战场配置来自 `config/battlefield_map<ID>.dat`、`pvedata.dat` 和 `prop.dat`；开局协议明确包含 `SpawnSeed` 和 `ItemSeed`；消息表另有 `NOTIFY_DISPATCH_ITEM`、`NOTIFY_PRODUCE_ITEM`、`NOTIFY_NPC_DROPITEM`。

15:03 实际会话没有任何 `NOTIFY_DISPATCH_ITEM`，四个 NPC 和本地玩家的死亡事件也全部 `ItemCount=0`。`pve07_8.map` 静态解析同时确认有 51 个 `LifeTime=1` 的可炸毁 ID 17101 元素。因此“没有爆出任何物品”不能继续只归因于随机运气。

客户端静态路径进一步确认了职责边界：

- `Client+0x20E288` 从本地地图的物品 ID 容器和坐标容器构造 schema `0x0FAE`；普通项上限 64，每项为 ItemID/Row/Col，延时服务项上限 32，每项还带 DispatchTime。
- 同一函数通过客户端既有事件编码/提交路径发出对象，符合 GAME_BEGIN 指定 `ArbitratorPlayerID` 后由仲裁客户端生成初始随机状态、服务端中继的架构。
- `Client+0x203F01` 处理收到的 `0x0FAE`，再次限制 64/32 上限，将延时项的 Row/Col 并入统一六字节物品数组，再调用地图安装函数。

2026-08-06 的 QQTEncoder 探针和静态消费路径补全了字段布局。`GAME_BEGIN_DATA` 中每个 `GAME_ITEM_TYPE` 精确为 `ItemID(uint32)+Quantity(int16)`。17:28 的实际会话把四种恢复补给发在全局 `Items` 后，约一分钟出现了用户识别出的普通地图飞鸭投放 NPC；没有地图掉落。`Client+0x1E2975` 确认 `Items` 是延时普通投放列表。

20:22 的地图 1601 实际复测把这四种补给移到全局 `NewItems` 后，客户端依次报告“初始化道具元素失败”和“创建游戏场景失败”，停留在房间但切换为关卡音乐。静态 `Client+0x1D9815/+0x1CB79A` 解释了完整因果链：`NewItems` 会立即按地图坐标创建场景对象，而 20020/20043/20044/20045 都不在场景元素工厂接受范围，首个空对象就会中止场景。它们只能作为背包消耗品，不能充当开局地图元素。

当前 Go 已完整编码/解码三组数组并按各自语义校验：玩家 NewItems 10 种、普通 Items 32 种且展开不超过 64 个、地图 NewItems 100 种。跨地图的 `adventure_initial_elements` 已删除；49 个关卡现在分别引用所属路线的普通材料池，加载时强制墙池条目为 `kind=material`。开局按 ItemSeed 执行 5 次独立 35% 抽样，生成 0..5 个墙内基础材料并交给客户端原生路径安放到本关允许的可破坏墙位置；这比旧版每关固定 5 个更接近资料估算且避免墙内物品过密。普通 Items 继续为空，避免再次启动普通模式飞鸭投放 NPC。玩家 NewItems 只来自该人物 SQLite 背包中 `ItemStatus!=0`、数量非零且角色匹配的已装备物品。

怪物掉落不由 Go 在死亡时伪造坐标或实体。服务端在每关开始时通过 `0x138A / CREATE_PVENPC_BOSS` 把该关 NPC 类型及已经抽样后的库存交给客户端；仲裁客户端死亡路径据此构造 `0x116B` 并交给服务端中继。当前静态 JSON 为 12 条路线分别维护普通、首领和墙体池，使用确定性加权无放回抽样：资料可用路线的普通组以 38% 安装最多一项，首领/特殊组以 95% 安装最多三项；资料未知的迷之底使用 33%/90% 的低置信保守池。候选 `weight` 是相对权重，不是官方掉率。库存非空时，原客户端仍会在死亡时随机选择 1..N 项生成。`PVEBOSS_INFO` 以 BossID 分组并把库存复制给同类型实例，所以重复怪会共享本局服务端候选结果，这不是已经证明的官方逐怪独立概率。某局抽样、坐标和所选地图均不写入 SQLite。多人同步仍必须在第二客户端加入后逐项确认，不能把单人回显直接宣称为完整多人权威逻辑。

`Client+0x201FEC` 先从模式对象虚函数 `+0x1C` 取得怪物掉落向量，只有向量非空才构造独立的 `0x116B / NOTIFY_NPC_DROPITEM`。该向量由收到 `0x138A` 后的 NPC 初始化代码写入；旧 Go 从未发送这条初始化消息，才是原先所有怪物零掉落的根因。地图 1649 已实际验证初始化后八只怪均能生成、拾取并结算物品。当前生成器进一步从全部 49 个已安装 `battlefield_map<ID>.dat` 的解码结果恢复 467 个 NPC 实例及分组，在 12 条路线、所有关卡开局/换关时下发对应库存；精确的腾讯线上概率表不在数据包中，当前候选内容属于可编辑的本地等价策略，不冒充官方原表。

相邻 `0x0FA8..0x0FAB` 已确认是玩家对玩家的击杀/救援请求与通知：仲裁客户端验证距离、队伍并生成后续通知。它们不是 NPC 击杀事件，也不能被服务端用于虚构怪物掉落。`0x0FAC/0x0FAD` 则是拾取请求/通知。Go 已对这些消息严格解析和具名日志，为多人测试保留原仲裁流程。

## 死亡与结算

2026-08-05 15:03 的实际单人会话中，客户端依次报告 NPC 30033、30035、30034、30036 死亡，然后请求 1602，最后报告本地 PlayerID 1 死亡。旧解析器只跳过两字节 schema，遗漏了 DWORD schema 的高 16 位，使业务主体错位并提前结束对局。临时修复虽然通过额外跳过两字节恢复了字段位置，却把这两字节错误命名成 `GameDataSequence`；最新 QQTMsgData、客户端回调和 QQTEncoder 往返证据已纠正该命名。

`QQTMsgData.bin` 完整字段表和客户端自身构造代码确认 `NOTIFY_GAME_OVER` 主体由 Time、结果计数、最多八项可变长度 `QQT_GAME_RESULT_DATA` 和末尾 GameMode 组成。每项依次为 PlayerID、Result、Remark、Point、FieldCount、`FieldValue1[FieldCount]`、`FieldValue2[FieldCount]`，FieldCount 最大为 4；无扩展的单人主体为 18 字节。Go 代码现已为信封、死亡、掉落项和可变结算结果建立具名类型及严格长度检查。

22:25 的负面样本先证明上行 REQUEST_PLAY 外壳不能直接用于服务器通知。15:04 的下一轮已经实际部署正确 `0x041B`：死亡和 GameOver payload 均可严格解析，但外层仍使用 `0x0083`，用户再次确认死亡无结算。只读命令表随后明确给出 `0x0083 ID_CMS_REQUESTPLAY` 与 `0x0084 ID_SMC_NOTIFYGAMEEVENT`，既有 `0x0084` 隔离实验也唯一触发 QQTEncoder schema `0x041B`。Go 现保留 `0x0083` 关联确认，把死亡、掉落、换关和 GameOver 主动推送全部改为 `0x0084 + 0x041B`，使用非零 32 位服务端事件序号；该命令路由构建仍需实际客户端验收。

战斗状态不再属于单条 TCP 连接，而是登记在服务端级 `GameID` 注册表。多个连接属于同一房间对局时读写同一个带锁的 `AdventureBattle`；测试覆盖“两人中首人死亡不结算、末人死亡结算、重复死亡不二次结算”。活动连接会投影共同 GameID/MapID，GAME_BEGIN 与对局通知使用各接收者自己的 envelope/UIN 重新封装。整场结算只推进房间状态一次，但会为每位在线参与者分别提交其结果、经验和拾取物并刷新背包；真实双客户端显示与断线边缘仍待验收。

客户端 `0x0FA7` 处理路径已经直接区分结果：本地玩家死亡构造 `Result=0`，敌对阵营成员死亡并触发本方结算的分支构造 `Result=2`。结合用户确认的失败哭泣/失败音效与成功欢呼/成功音效，Go 现将两值定义为具名 `GameResultLoss` 和 `GameResultWin`；它们只决定本局结果演出，不代表人物档案存在探险胜负场。Remark、Point 和其余旧结果值仍保持未命名。单人全员淘汰只生成 Loss，客户端自己上报的成功 FBB 则保留其 Win 值中继。

17:28 的两层隔离解码只证明 `0x03FB / REQUEST_PLAY` 和 `0x0FBB` 业务主体各自合法；22:25 的回调跟踪确认错误推送连 `Client+0x1A23BC` 都没有到达。随后 QQTEncoder 对死亡通知 `0001 00000001 0000000F A70F0000 ...` 以 schema `0x041B` 成功解码并逐字节往返，但 15:04 的实际部署又证明 payload 合法仍不能弥补错误运输命令。静态状态链表明正确的 `0x0084 + 0x041B` 到达后才应由 `Client+0x1A3AB0` 轮询队列、再由 `Client+0x1A3B5F` 解码并展示 GameOver；实际结算成功后才接入 SQLite 战绩/经验事务。
