# 家族系统

日期：2026-08-16（Asia/Shanghai）

家族使用独立的 SQLite 关系模型，不再把成员关系仅塞进人物 JSON。人物协议中的 `KinIndex`、
`KinName`、`KinFlagID` 是由关系表投影出的缓存字段；登录、大厅个人资料和房间成员继续使用原版
字段位置。

## 已实现链路

- 创建家族：`0x00B5 / 0x1771`。名称和文本按 GBK 字节上限验证；账号须持有 100 份盟约书
  `1077` 或 1 份超级盟约书 `2235`。原说明写的是“拥有”，因此资格物当前不消费。
- 家族资料与成员：`0x00B6/0x00B7`，返回 `KinBase` 与最多 200 个 `KinMemInfoOld`。
- `KinMemInfoOld.Status` 的 bit 0 是客户端 mode-3 在线成员缓存的分组位，bits 24..27 则是
  QQTSection `GetKinPositionByUin/GetKinMemberHonor(mode=1)` 实际读取的职位等级。响应按当前活动
  主游戏连接实时置/清 bit 0，并把持久层 `authority_id` 投影到高位；线上的独立 `Grade` 字段
  仍同步保留，但界面职位和本地邀请权限并不读取它。
- 家族聊天：`0x00BE → 0x00BF`，仅投递同家族在线成员，并按接收者信封重新编码。
- 成员管理：踢出、主动退出、解散、成员权限，分别使用 `0x00C0/0x00C1/0x00C2/0x00C5`；
  所有变更与人物家族投影在同一事务提交。
- 直接邀请：`0x00BA -> 目标0x00BC -> 回答0x00BC -> 最终0x00BD`。邀请和审批最低等级10；
  待处理邀请按目标唯一并在十分钟后失效，接受时成员关系、人物投影和邀请消费原子提交。
- 成员变更事件：原生 `0x00C4/0x178A` 的事件1/5/8/9分别表示加入、解散、移除、公告更新。
  踢人和解散会直接通知被影响成员，不能只等待成员列表轮询。
- 文本和标志：两个头衔入口 `0x00B8/0x00C6`、宣言 `0x0140`、通知 `0x0141`、徽章
  `0x00C7` 均使用各自原始请求/响应结构。`0x00C9/0x00CA` 只保留为旧请求别名；当前 5.2 客户端
  实测通过双向外层命令 `0x0140/0x0141` 携带请求与响应 schema。
- `KINFLAGID` 不是不透明的八字节整数，而是客户端 SWIG 对象中的
  `m_dwIndex:uint32 + m_iFlagID:int32`。原版 UI 以第二个 DWORD 选择 `kinTotem-%03d`；内建一号
  徽章因此编码为 `00000000 00000001`。SQLite schema 16 只迁移历史错误默认值
  `00000001 00000000`，不改写玩家选择的其他徽章。
- 空公告在领域层仍是空字符串，但 `KinBase` 线上编码为“长度 1 + NUL”。原生发布按钮先用缓存长度
  调用 `strncmp`；长度为零时任何首次输入都被误判为未修改，从而根本不发送 `0x0141`。单个 NUL
  保持 UI 空白，同时令首次非空公告能够通过客户端的变更判断。
- 公告保存成功后，`0x0141/0x1796` 响应只显示结果，不刷新本地缓存。服务端随后向本人和同家族
  在线成员下发原生 `0x00C4/0x178A` event 9，以公告正文更新客户端缓存；关闭并重开家族页时再由
  SQLite 中的权威 `KinBase` 恢复。
- 排行：`0x00CB / 0x1797` 同时返回荣誉和活跃度前 20。`TopKinInfo` 的 40 个固定
  `KinOrderInfo` 槽按“荣誉 20 + 活跃 20”投影；没有历史快照时 `BeforeOrder` 等于当前名次，
  不伪造排名涨跌。
- 删除账号：普通成员删除会推进成员表版本；删除族长账号会先事务性解散家族并清除其他成员投影，
  不再被 `owner_uin ON DELETE RESTRICT` 卡住。

## 等级、权限与容量

原版不是“普通/管理/族长”三级，而是固定五级数字合同：族长12、长老10、堂主8、护法6、
弟子4。升降每次只能变动一级；提升对象须至少低自己两级，降低对象须至少低自己一级。族长由
`owner_uin` 唯一确定且不可改级，不实现职位转让。

邀请/审批允许长老及以上执行；踢人、解散、宣言、公告、徽章和五个职位名修改仅族长可执行。
自定义职位持久化必须恰好包含五个非空名称，SQLite 使用 ASCII `0x07` 分隔并保留尾部分隔符；
线上 `KinBase.Title` 及设置职位消息则是 ASCII 十进制分帧对象：数量、等级和长度均用
`"%d "`，名称用 `"%s "`，其中长度包含名称后的尾空格。旧无尾空格编码会被客户端复制成
单字，误写成二进制对象则会全部显示为空。

成员容量来自 `KinBase.Status` 高12位，当前本地恢复规则为100；协议成员数组最多200只是线格式
上限。schema 17 把旧三级权限、空职位名和缺失容量原地迁移为上述合同。

数据表为 `kin_families`、`kin_members`、`kin_applications`、`kin_invitations`。同一账号最多属于
一个家族；同一家族名称唯一；同一目标同时最多缓存一份直接邀请。

## 有意保留的证据边界

直接邀请 `DoKinTask(mode=4)` 的 `Para=0/Reserve=0` 及接受/拒绝枚举已经由客户端发送与接收路径
闭合。家族列表上的主动申请仍缺完整 UI 枚举样本，不能把邀请枚举外推过去。自定义 2048 字节
旗帜上传 `0x00B9` 仍保留为后续实机样本项；普通徽章、公告 event 9 和八字节 `KinFlagID` 已类型化。

原版家族界面已经证明创建、重登后成员关系和成员列表可恢复。2026-08-16 的当前 5.2 客户端实测
确认：schema 16 徽章不再显示为蓝色空块；首次公告通过原生 `0x0141` 发布，SQLite 保存后收到
`0x0141/0x1796` 成功响应与 `0x00C4/0x178A` event 9，关闭重开页面仍显示公告。
同日又从 QQTSection 的 mode-3 缓存构建函数确认成员在线位，并完成实时主连接投影；进一步的
运行时缓存快照和 API 静态链确认职位必须同时投影到 `Status` bits 24..27。此前 SQLite 中族长
`authority_id=12`、线上的独立 `Grade=12` 均正确，但 `Status` 高位为0，正好解释了个人职位空白
以及客户端在发送 `0x00BA` 前本地拒绝邀请。该投影已修复并加入关键回归。

完整静态函数、协议方向、权限和事务证据见
`evidence/kin-native-management-and-invitation-v1.md`、
`evidence/kin-native-title-wire-v2.md`和`evidence/kin-member-status-authority-v1.md`。
